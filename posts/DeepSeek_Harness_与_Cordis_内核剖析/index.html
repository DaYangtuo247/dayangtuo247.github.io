DeepSeek Harness 与 Cordis 内核剖析

人工智能工程实践 # Agent# DeepSeek# Cordis# 论文阅读# TypeScript
Sep 13, 2026
41 min read
—

2026 年 8 月 13 日，DeepSeek 开源了自家的 agent harness——仓库 deepseek-ai/deepseek-harness，命令行叫 dsh，MIT 许可，纯 TypeScript。副标题只有一句话：Everything is a Plugin.

同一天，另一个仓库也悄悄建了起来：cordiverse/paper。两周后论文挂上 arXiv，名字叫《A Programming Paradigm for Spatiotemporal Composability》，92 页，作者是北大的 Yifan Shi、Wei Zhang 和 DeepSeek 的 Tianyi Cui。

这就是有意思的地方。别家开源 agent 框架，README 里写一句「我们是模块化的」就完事了。DeepSeek 开源了一个框架，外加一篇论文，专门论证「模块化」这件事在数学上该怎么定义。

这篇文章想说清三件事：dsh 长什么样、它底下的 Cordis 内核给了它什么、论文到底在解什么问题。

Agent = model + harness

一个能干活的编程 agent，模型只占一半。

另一半是工程层：读写文件、跑终端、搜索、管上下文、做计划、调度 subagent、把这一切记成可回放的会话。这一层就是 harness。

同一个模型换个 harness，实际能力差距可以非常大。这也是为什么各家在模型之外还要卷这一层。

dsh 的立场比较极端：harness 里没有一块是特权代码。模型适配器是插件，工具注册表是插件，会话日志是插件，连 agent loop 本身都是插件——全都能在配置里换掉，不用改一行源码。

有多极端？看两个数字。

内核不认识「agent」这个词。它只认识组件、副作用和依赖

这就是 dsh 架构的全部秘密：没有需要打补丁的特权内核。扩展它的方式是把插件挂到别的插件旁边，而所有注册都是副作用，插件卸载时自动撤销。

dsh 是怎么装起来的

跑起来的 dsh 是一棵插件树，由启动时按序叠加的几层拼成。

记住三个名词就够了。profile 是一份具名装配，随发行版交付的模板有 web、headless、sdk、sdk-minimal、acp 五个。组合包是「配置 + 挂载代码」的分发格式，dsh-base 提供模型适配器、工具、持久化、沙箱、凭据、遥测这些共享底座。patch 是覆盖层，按 id 定位某一行，替换它整个 config，或者插入新行。

条目在列表里的位置不决定谁先启动——那由服务依赖决定

所以想换掉某个能力，不用 fork 仓库，写条 patch 就行。想知道有哪些行可以换：

dsh --profile web --dump-config

有个细节能看出这套东西的克制：web profile 默认实时重载 patch，而 headless、sdk、acp 只在启动时应用一次——一次性运行或 stdio 应用拿到工作之后，中途替换它的依赖会破坏生命周期。热替换不是「永远开着更好」的特性。

骨架服务

Cordis 的服务都挂在上下文的稳定键上，dsh 的骨架大致是这些：

包职责ctx 键
core/session仅追加的会话事件日志ctx.sessions
core/system-prompt提示词片段与工具 schema 的组装ctx.systemPrompt
core/tools工具注册表 + 带把关的执行流水线ctx.tools
core/agentAgent 接口与活跃 agent 注册表ctx.agents
core/agent-loop实现该接口的默认驱动器ctx.agentLoop
llm/llm消息与流式词汇表，适配器 seamctx.llm

注意 core/agent 和 core/agent-loop 是两个包：前者定义「什么是 agent」，后者是「默认怎么驱动它」。想换一套循环策略，替换后者即可，ctx.agents 的消费方（UI、SDK、遥测）一行不改。这就是「agent loop 本身也是插件」的具体兑现方式。

能力 seam

dsh 文档里反复出现一个词：seam（缝）。一个 seam 是包含三种角色的可替换能力——

seam 是完整能力，绝不是其中某一个角色

文档里有句话点破了它的价值：文件系统和进程提供方共享同一个执行世界，所以把它们指向远程沙箱，就等于把 Bash、PTY 和 LSP 一并搬了过去，不用给每个提供方单独做 fork。

顺带一提，dsh 并不绑死 DeepSeek 自家模型。设置页里能直接添加 anthropic、openai、moonshotai（Kimi）、zai（GLM），也能填自建网关。

一次轮次

两个术语先记住：步骤是一次模型请求，加上它引发的工具执行；轮次是一次对已接纳输入的排空，包含零个或多个步骤——是的，可以是零个，agent/pre-step 把首批消息拒了，轮次就不花任何步骤地关闭。

sequenceDiagram participant U as 用户 participant A as Agent inbox participant D as agent-loop 驱动器 participant P as ctx.systemPrompt participant L as ctx.llm participant T as ctx.tools participant S as 会话日志 U->>A: followup(content) A->>D: 排队的工作唤醒驱动器 D->>S: turn/start D->>P: system-prompt/assemble（waterfall） D->>D: agent/pre-step（waterfall）→ enter / reject D->>S: step/start D->>L: agent/request（waterfall）→ prepareCall D->>S: system/message · user/message · request/header D->>L: 绑定后的调用经 llm/stream 发出 L-->>D: StreamChunk*（agent/assistant-stream 实时帧） D->>S: assistant/message（内嵌紧凑带时间 stream） D->>T: tools/pre-execute → execute → post-execute T-->>S: tool/call · tool/result D->>S: step/end D->>D: agent/turn-stopping（serial 终止检查点） D->>S: turn/end

两个容易被忽略、但很关键的设计：

取消发生在提交之前。 agent/request 和 prepareCall() 先解析实际路由，再提交系统提示词和已接纳的用户消息。在任一异步阶段取消，这两者都不会被提交——不会留下「用户消息进了日志、请求却没发出去」的脏状态。

模型可见即已记录。 这是一条带运行时断言的不变量：抵达模型请求的一切都必须能从会话日志重建。它的直接后果是——新增一项模型可见输入，就必须新增一个会话事件。

Cordis 内核

Cordis 不是 dsh 现攒的。它 2022 年就有了，作者说名字取自拉丁语的「心」——这颗心一共 2,693 行。

插件作者要知道的东西可以压成三句话：

  1. 插件就是一个函数，Cordis 调用它的时候递给你一个 ctx。
  2. 服务住在 ctx 的稳定键上，别人按 key 找你，不 import 你。
  3. 所有注册都是可撤销的副作用，插件卸载时自动回滚。

第三条是全部的重点。

获取与释放写在一处

对于 Cordis 还管不到的资源（定时器、连接、watcher），包进 ctx.effect() 并返回释放函数：

import type { Context } from '@deepseek-ai/cordis'

export const name = 'heartbeat'

export function apply(ctx: Context) {
  ctx.effect(() => {
    const timer = setInterval(() => console.log('tick'), 200)
    return () => {
      clearInterval(timer)
      console.log('heartbeat cleaned up')
    }
  })
}

对比一下 VSCode 的 activate / deactivate：那套 API 把副作用的创建和销毁分在两个函数里，作者得自己记住配对——论文管这叫违反关注点局部性，并指出它让「完整清理」难以验证。ctx.effect() 的形状强制两者写在一处。

大部分时候你甚至不用手写它，因为内置 API 本身就是 effect：ctx.on() 的监听器会在卸载时移除，ctx.plugin() 的子插件随父插件一起释放，ctx.tools.register(...) 也会把释放函数附到调用插件上。

有个坑：释放函数按注册的逆序启动，但多个异步释放函数会并发跑。如果拆除步骤必须严格有序，把它们放进同一个释放函数里依次 await。

依赖消失就下线

服务用 Service 子类提供，消费方用 inject 声明：

export const name = 'consumer'
export const inject = ['greeter']

export function apply(ctx: Context) {
  // 声明了 greeter，进到 apply 就保证 ctx.greeter 已就绪
  console.log(ctx.greeter.greet('world'))
}

关键在这句：inject 不是一次性的启动检查。应用运行期间所需服务消失了——提供方被卸载或热替换——每个依赖插件也会跟着卸载，等服务回来再重新加载。

这正是「配置里能换服务」的原因：卸载 dsh-bash-local，挂上另一个 shell 提供方，所有 inject: ['shell'] 的插件重启并用上新实现。

软依赖则不写 inject，在用的地方探测就行：

const greeter = ctx.get('greeter')   // 没有提供方时是 undefined，插件照样运行
console.log(greeter?.greet('maybe') ?? 'no greeter available')

Fiber 状态机

每个已加载的插件实例都有一个 fiber，即运行时句柄。

上下两半是同一个状态机：论文的 Reloading 就是实现里的 LOADING

PENDING 是个正常状态，不是错误——提供方可能稍后才挂上。这也是「为什么我的插件没输出」最常见的答案。

热替换就是这台状态机跑一圈：卸载释放 effect，加载遵循依赖，中间把模块代码换掉而已，不需要开发者标注任何「接受边界」。

插件之间通信走类型化事件，一共五种分发模式：

模式是否 await有返回值典型用途
emit否否广播通知
waterfall否是环绕中间件，可包装可短路
parallel是否并行扇出
serial是是按序执行
bail否是停在首个 bail 值

其中 waterfall 最有意思：监听器收到 (...args, next)，调 next() 执行下游，不调就是短路。dsh 的 agent/pre-step、agent/request、llm/stream 和三个 tools/* 都是它——于是「权限门禁」「超时」「指标采集」这类横切关注点能自然地一层层叠起来。

自进化的两道坎

铺垫到这里，可以进正题了。

软件世界有个反直觉的事实：大多数插件系统，卸载一个插件要重启整个宿主进程。删掉的可能只是一个插件，陪着它一起重启的却是所有插件。

说是「插」件，实际上插上去就拔不下来。

VSCode 是典型案例。论文自己去 Marketplace 数过（2026 年 6 月 9 日）：按安装量排名前 100 的扩展里，87 个含可执行代码，一旦激活就没法在运行时单独卸载。而声明了对非内置扩展依赖的，只有 7 个——后一个数字说明的不是「大家不需要依赖」，而是 API 形状根本没鼓励依赖。

放在普通软件里，这最多算麻烦，重启一下也就过去了。

但 agent 不一样。

论文切入自进化的角度是这样的：未来的 harness 可能一边服务请求，一边自己生成一个工具、自己装进运行时、发现有问题再自己把它换掉。如果每改一行都要重启整个进程，之前攒的上下文和缓存全得重来；更糟的是，一次有缺陷的自我修改，可能把「用来恢复的那个进程」本身搞挂。

这是时间上的那道坎。

如果模块之间的依赖靠各自打补丁——今天检查一下有没有 A，明天猜一下 B——迟早会引入循环依赖，等到 reload 的时候才爆。

这是空间上的那道坎。

静态设定下，这两维分别退化成词法作用域和 import 解析；一旦动态，两个都变难

那「重启就好了」这个万能答案呢？论文的回应很干脆：操作系统在进程粒度上给你时间可组合性，容器编排在服务粒度上给你空间可组合性——可现代软件的组合粒度早就细到进程以下了。粒度对不上的代价，就是每次重启丢光进程内状态（缓存、连接、部分计算），重建要数秒到数分钟，为了维持可用性还得堆冗余副本。

DeepSeek 的解法

论文的技术路线可以一句话概括：把编译期的 effect / coeffect 概念，搬到运行时。

  • **effect（效应）**刻画程序对世界的影响；
  • **coeffect（余效应）**刻画世界对程序的约束。

一个管「你改了什么」，一个管「你需要什么」。刚好对上前面两道坎。

时间维：可逆 effect

核心定义只有一句：每个对上下文的修改，都必须配一个显式的逆函数。

加载插件时，每改一次状态就把对应的逆记下来，按顺序叠成一条撤销链；卸载时反向执行这条链，系统状态就精确回到插件装上之前的样子。

像一摞盘子——最后放上去的那只，先拿走。

形式上，上下文从「只有状态」变成了「状态 + 撤销链」

想看一眼数学长什么样的话（跳过完全不影响阅读）：论文把上下文类型从 Γ\GammaΓ 抬成

∂Γ≔Γ×(Γ→Γ)\partial\Gamma \coloneqq \Gamma \times (\Gamma \to \Gamma)∂Γ:=Γ×(Γ→Γ)

也就是一对 (γ,φ)(\gamma, \varphi)(γ,φ)，γ\gammaγ 是当前状态，φ\varphiφ 就是那条撤销链。后面一串定理都在证同一件事：追踪不改变正向行为，而且只要每个逆都真的能撤销它对应的副作用，恢复就一定回到起点。

这里有条必须说清楚的边界：运行时并不校验这件事。回调交上来一个逆，但「这个逆真的撤销了那个副作用」是组件作者的义务，不是运行时验证的性质。Cordis 给你的是一套结构和纪律，不是一个证明器。

空间维：反应式 coeffect

组件声明自己需要哪些依赖。比如一个聊天插件说，我要一个消息适配器和一个数据库——两个都在，它才进入 ACTIVE；缺一个，它就老实待着，不急着启动，也不会先跑起来再因为空引用报错。

反过来也成立：提供方出现，依赖方自动激活；提供方要撤走，依赖方先停下来、把自己的 effect 撤回，提供方才完成卸载。

这套拓扑编排不靠开发者手写，是从声明里推出来的。

这就是 inject 在运行期持续生效、而不是只做一次启动检查的形式化解释

论文很克制地指出，这条只给出局部保证。「撤回一个绑定要等它引发的停用全部完成」和「激活期间读到的绑定不能被挪走」这两件事它管不了——因为那是对别的组件的约束，得留到全局的元理论里去证。

理论与代码的对照

ctx.effect 的实现思路也不复杂：每次迭代把新的逆前插进累积器（于是恢复天然是 LIFO），dispose 用一个 armed 标志保证至多触发一次，最后把自己的释放函数挂到父上下文的累积器上——子 effect 的逆，本身又是父上的一个 effect。整套设计的递归结构就是这么来的。

实证：Koishi

论文的实证部分不是跑分，是一个聊天机器人框架。

Koishi 基于 Cordis 构建，四年积累了 4000 多个社区插件，从 IM 适配器、数据库驱动到管理控制台和各类终端功能。顺带一提，它的名字和图标来自东方 Project 里的古明地恋；而论文一作正是 Koishi 的作者。

论文从中读出三件事：

  • 表达力与通用性：Koishi 的每个功能都是插件，框架本身只贡献聊天机器人的领域词汇。而且同一套模型在完全不同的运行时里复现了一遍——Koishi 的 Web 控制台是第二个独立的 Cordis 应用，它的插件组合的是浏览器和 UI 的原语。
  • 零认知负担：从控制台禁用一个插件，它的影响就地撤回，其他插件继续工作；开发时保存即热重载，别处的缓存和连接纹丝不动。哪怕没经验的作者也不用写卸载路径——正确性从「靠每个人自觉」变成了「由抽象一次性兑现」。
  • 开放生态：切换存储后端或重连适配器时，只有解析到的依赖真的变了的插件才会重新激活。这些插件通常出自不同作者之手，彼此唯一的协调就是那个 coeffect。

论文也没把它包装成完美 demo：单一生态、单一语言，是观察性的而非对照实验，抽象开销和对生产力的影响都还没量化——这些是它自己写的。

写一个工具插件

跑起来只要一条命令：

npx @deepseek-ai/dsh web

默认在 127.0.0.1:3080（明文 http）起 Web UI，本机启动时会顺手打开浏览器。

工具是最常见的扩展点，最小形态长这样：

import { readFile } from 'node:fs/promises'
import type { Context } from '@deepseek-ai/cordis'
import { defineTool } from '@deepseek-ai/dsh-tools'

export const name = 'my-tool'
export const inject = ['tools']

export function apply(ctx: Context) {
  ctx.tools.register(defineTool({
    name: 'read_file',
    description: 'Read a file from disk.',          // 模型看到的就是这句
    parameters: {
      path: { type: 'string', required: true, description: 'Absolute path' },
      limit: { type: 'number' },                     // 默认可选
    },
    output: {
      schema: { type: 'string' },
      render: (_args, value) => [{ type: 'text', text: value }],
    },
    async execute(args, exec) {
      // args 由 schema 推导出类型：{ path: string; limit?: number }
      return readFile(args.path, { encoding: 'utf8', signal: exec.signal })
    },
  }))
}

把这段代码对回前面的概念：inject = ['tools'] 就是 coeffect 声明，apply 就是 effect 函数，ctx.tools.register(...) 的注册是副作用——dispose 掉这个插件的 fiber，就等于注销这个工具，你不需要写任何卸载代码。schema 也会自动流进系统提示词的组装。

两条 dsh 特有的约定值得记：参数在 execute 跑之前已经按 schema 校验过了；execute 只返回规范 JSON 值，给人看的解释放进 output.render。另外别把部署策略写进工具——允许／拒绝／询问用 tools/pre-execute，超时和指标用 tools/execute。

dsh 的四种模式

dsh 的「模式」在内部叫 preset：一个 agent.cordis.yml 文件，按会话挂载。换句话说——你在下拉框里选的那个模式，就是一份插件清单。

随附四个：

模式官方描述它实际换掉了什么
标准模式功能完整的编码 Agent，支持文件编辑、Shell、文件与网页检索、Skills、计划、目标、子代理和工作流基准线，每进程挂载一次
PTC 模式同上，但默认不提供 workflow 工具；其余工具通过 PTC 模式 SDK 呈现工具注册表的呈现方式——模型改用一个 TypeScript 程序组合多步操作
极简模式仅提供持久 shell 的单工具编码 Agent固定提示词、不注入运行时上下文、没有上下文压缩，给跑分用
创造模式标准模式的全部能力，外加运行时检查、插件实验和 preset 创作指导加上读写自己所运行的那个 runtime 的能力

PTC 模式那行值得解释一句：它换掉的不是工具本身，而是工具怎么呈现给模型。注册表被生成成一份 SDK，模型可以 await tools.<name>(args) 直接调用，于是一段本来要五次往返的操作变成一次。

模式换不掉什么

这里有个容易误会的地方。preset 是 agent 平面的组合，它能带来的只有三样东西：工具、提示词段落、skill。

注册表本身、沙箱与审批栈、持久化、模型路由——这些属于 host 平面，preset 不许拥有。所以换模式不会顺带把你的权限策略换掉；同一个进程里可以跑着不同模式的会话，各自的状态互相隔离。

两条配套规则：只有空会话能切换模式；subagent 会加入父方的组装，因此它看到的工具和提示词跟创建它的 agent 完全一样。

还有个细节能看出这套东西有多严格：preset 里的 service 行必须放在带 isolate 的组里，否则它会发布到根 realm 变成进程全局的，第二个挂载同一 preset 的会话就会跟第一个撞车——dsh-agent-presets 在挂载时直接拒绝。

创造模式：让 agent 去写 agent

这个模式值得单拎出来，因为它就是前面那条自进化线的产品形态。

它的 preset 文件开头写得很直白：存在的理由是「让一个人可以叫 agent 去写另一个 agent」。标准模式的东西一样不少，加的是自指的 Cordis 工具集、一个教你怎么写组合的 skill，以及一个会说明「这次改动属于哪个平面」的 persona。

同一个文件里还有一段全大写的 TRUST 警告，我原样转述：cordis_mount 会对活跃运行时求值模型写的 JavaScript，而这个 agent 写出来的组合会成为别的会话挂载的 preset——把跑在这个模式上的会话当成 shell 访问来对待。

论文里那句「未来的 harness 可能一边服务请求，一边自己生成并部署对自身组件的修改」，到这里就不是设想了，是下拉菜单里的一个选项。

总结

「一切皆插件」是有代价的。 65 万行 TypeScript、275 个 package.json，任何一个具体问题的调用路径都要穿过好几层服务和事件。dsh 自己的文档里那句「建议使用 agent 探索代码库并理解其架构」，读起来半是自信半是自嘲。

最值得偷的一课，其实和 agent 没什么关系。 是那个把「获取资源」和「释放资源」强制写在同一个闭包里的 ctx.effect()，以及「依赖消失就自动停用依赖方」的 inject。这两个东西跟 LLM 一点关系都没有，但你下次写任何一个需要动态加载模块的系统时，都会想起它们。
