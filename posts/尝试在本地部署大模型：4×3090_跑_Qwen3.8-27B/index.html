模型介绍

Qwen3.8-27B 是阿里 Qwen 于 2026 年 8 月发布的开源权重模型，采用 Apache 2.0 许可。同期发布的还有 2.4T 参数的 Qwen3.8-Max，但与个人硬件真正相关的是这个 27B 版本——它是稠密模型而非 MoE，尺寸面向单机部署设计。它同时是原生视觉语言模型，可直接处理图像与视频输入，涵盖 STEM 图表、文档乃至小时级视频。

规格
模型类型带视觉编码器的因果 LM
参数27B 稠密（BF16 磁盘约 28B）
隐藏维度 / 层数5,120 / 64
隐藏布局16 × (3 × (Gated DeltaNet → FFN) → 1 × (Gated Attention → FFN))
线性注意力头48 V / 16 QK（Gated DeltaNet），维度 128
注意力头24 Q / 4 KV（Gated Attention），维度 256
FFN 中间维度17,408
上下文原生 262,144 token，可通过 YaRN 扩展至 1M
输入 / 输出文本、图像、视频 / 文本
许可Apache 2.0

架构上，64 层并非同构堆叠：每 4 层中 3 层用 Gated DeltaNet（线性注意力，降低长上下文开销），1 层用 Gated Attention（保留全局建模能力），如此循环 16 次，再配合多 token 预测加速解码。这套结构较新，推理框架版本必须跟上。

一、硬件与环境

上述规格决定了本次部署会遇到的主要约束：稠密结构意味着每生成一个 token 都需读取全部 27B 参数，解码速度受限；混合注意力较新，框架版本需要足够高；262K 上下文虽然可观，但 KV cache 须按此上限预留显存。

项目配置
GPU4 × RTX 3090（24GB × 4），驱动 580.159.03 / CUDA 13.0
框架vLLM 0.28.0（需 0.17.0 以上，该版本起提供 Gated DeltaNet kernel）
模型Qwen3.8-27B，BF16 约 51.7GB
并行张量并行 TP=4

二、启动参数

python -m vllm.entrypoints.openai.api_server \
  --model "$MODEL" --served-model-name qwen3.8-27b \
  --tensor-parallel-size 4 \
  --gpu-memory-utilization 0.95 \
  --max-model-len 262144 \
  --chat-template "$TEMPLATE" \
  --enable-auto-tool-choice \
  --tool-call-parser qwen3_xml \
  --reasoning-parser qwen3 \
  --host 0.0.0.0 --port 8000

其中三个参数彼此配套，任意修改一项都可能导致工具调用整体失效：

参数配置依据配错的现象
--tool-call-parser qwen3_xmlQwen3.8 的工具调用为 XML 风格而非 JSON，qwen3_coder 同样可用沿用教程中常见的 hermes 会解析失败，工具调用链路中断
--reasoning-parser qwen3生成提示预填了 <think>\n，模型输出自”思考中间”开始，不含起始标签思考过程与正式回答混合输出
--chat-template官方模板在工具调用与历史消息渲染上存在问题，改用社区增强版工具调用稳定性下降，且不影响多模态能力

Qwen3.8 输出的工具调用形如下例，与 hermes 预期的 JSON 结构并不匹配：

<tool_call>
<function=get_weather>
<parameter=city>武汉</parameter>
</function>
</tool_call>

三、显存占用情况

四张卡分别占用 23116 / 23093 / 23093 / 23095 MiB，数值高度一致，这正是张量并行的特征：每卡分到同等大小的权重分片。

用途每卡大小
模型权重（51.7GB ÷ 4）~13GB
激活值、CUDA graph、通信缓冲1-2GB
KV cache 池~8-9GB

vLLM 将总预算减去权重与运行时开销，其余全部预分配为 KV cache 池，切分成固定大小的块统一管理，请求从池中申请、用毕归还，池本身容量不变。由此产生两个容易误判的现象：nvidia-smi 的数值恒定，空闲与满负载时完全一致；GPU-Util 100% 也不代表算力跑满，解码阶段大部分时间在等待显存读写。

并发增加并不会提高显存占用，只会加剧池内竞争。池接近上限时新请求进入排队，完全耗尽时触发 preemption，将执行中的请求换出后重新计算。若需提升并发，可启用 --kv-cache-dtype fp8，KV cache 存储减半相当于池容量翻倍。

四、心跳日志

真实负载只能通过 vLLM 每 10 秒输出的这行统计判断。

Engine 000: Avg prompt throughput: 42.1 tokens/s, Avg generation throughput: 27.5 tokens/s,
Running: 1 reqs, Waiting: 0 reqs, GPU KV cache usage: 8.6%,
Prefix cache hit rate: 75.4%, MM cache hit rate: 75.0%
字段含义截图中的数值说明什么异常信号
Avg prompt throughputprefill 阶段的输入处理速率多数行为 0.0，表示该 10 秒内无新请求，引擎处于纯解码状态恒为 0 但客户端确在发送请求，说明请求未到达服务端
Avg generation throughputdecode 阶段的输出生成速率稳定在 28~29 tok/s，即这套配置的上限骤降说明并发升高或上下文变长
Running / Waiting执行中、排队中的请求数1 / 0，产能有富余Waiting 持续大于 0，说明受限于池容量或 --max-num-seqs
GPU KV cache usageKV 块池的占用水位三分钟内由 7.7% 升至 9.2%，单会话历史在增长长期低于 20% 说明窗口设置过大，超过 90% 则临近 preempt
Prefix cache hit rate前缀缓存命中率75%，agent 场景下本身就偏高骤降说明历史被改写或缓存块遭淘汰
MM cache hit rate图像 ViT embedding 缓存命中率恒定 75.0% 未变化，说明该时段无新图像输入纯文本服务可忽略

有三处容易读错。两个 throughput 均为 10 秒窗口平均值，一次仅几十毫秒的 prefill 摊入窗口后会显示为几十 tok/s，不宜据此估算真实能力；Prefix cache hit rate 恰好相反，是自进程启动以来的累计值，变化极为缓慢，由 74.5% 升至 75.4% 的背后是数十万 token 的积累；Avg generation throughput 统计的是全部并发请求的总吞吐，8 个请求并发时总量可达 90 tok/s，但单个请求仅分到 11 tok/s。

29 tok/s 偏低的原因在于 decode 属于 memory-bound：每生成一个 token 都要完整读取 51.7GB 权重。按每卡 13GB、RTX 3090 显存带宽约 936GB/s 计算，理论上限为 72 tok/s，实测仅达 40%，其余开销来自缺少 NVLink 而经 PCIe 的 all-reduce、长上下文下 attention 对 KV cache 的额外读取，以及 kernel 启动开销。

日志中还会穿插 POST /v1/responses HTTP/1.1" 200 OK 一类访问记录，可据此确认客户端实际使用的端点。排查工具调用失效时应先看这一行：若请求根本未到达，则问题出在客户端配置，与 parser 无关。

五、逐层验证

服务启动不等于可用。建议先用 curl 逐个验证三类端点，再接入客户端，这样出现问题可立即定位到具体层次。

能力端点验证要点
纯文本/v1/chat/completionsreasoning 与 content 是否为分离的两个字段
工具调用/v1/messages（Anthropic 兼容）是否返回 "type": "tool_use" 结构化 block，stop_reason 是否为 "tool_use"
多模态/v1/chat/completions更换自定义 chat template 后能力是否受损

工具调用是最容易出错的环节：

curl http://127.0.0.1:8000/v1/messages \
  -H "Content-Type: application/json" -H "anthropic-version: 2023-06-01" \
  -d '{
    "model": "qwen3.8-27b", "max_tokens": 512,
    "tools": [{"name": "get_weather", "description": "获取指定城市的天气",
      "input_schema": {"type":"object","properties":{"city":{"type":"string"}},"required":["city"]}}],
    "messages": [{"role": "user", "content": "武汉今天天气怎么样"}]
  }'

parser 不匹配时，整段 <tool_call> 会作为纯文本归入 "type": "text"，stop_reason 变为 "end_turn"。多模态测试中若服务器无法访问外网图片，可用 base64 传输本地文件，注意 base64 -w 0 需关闭自动换行，否则会破坏 JSON 结构。

模型识别出了主体、构图、背景倒影与光线，并读出了图片中央那处半透明的图库水印。

六、客户端接入

vLLM 同时提供三套 API，多数 agent 客户端均可直接接入：

端点协议典型客户端
/v1/chat/completionsOpenAI Chat Completions多数工具与 SDK
/v1/messagesAnthropic MessagesClaude Code
/v1/responsesOpenAI Responses部分新式 agent 框架

以 Claude Code 为例：

export ANTHROPIC_BASE_URL=http://127.0.0.1:8000
export ANTHROPIC_AUTH_TOKEN=dummy
export ANTHROPIC_MODEL=qwen3.8-27b
export ANTHROPIC_SMALL_FAST_MODEL=qwen3.8-27b

SMALL_FAST_MODEL 必须设置，否则后台小任务（生成标题、压缩上下文）会转而请求真正的 Anthropic API 并失败。未启用 --api-key 时 token 可任意填写，但不能为空。若客户端在本地而服务在远程，用 ssh -N -L 8000:127.0.0.1:8000 user@server 建立隧道即可，也无需将端口暴露到网络上。

七、真实任务实测

使用了一个需要多步工具调用的完整任务：

写一个网页版本的俄罗斯方块，要美观，然后我本地有 npm、nodejs 等，使用什么框架由你来定，然后使用键盘的上下左右按钮来控制，工作空间就在当前目录，你创建一个新文件夹，并启动这个项目。

不指定框架用于考察自主决策，创建目录、写入文件、安装依赖、启动服务用于考察多轮工具调用，“要美观”则用于考察默认审美。同一 prompt 在两个 agent 客户端各执行一次，其中一个将统计信息展示在状态栏。

指标数值
步数 / 工具调用23 步 · 24 次
LLM 耗时20 分 05 秒（工具执行仅 25.8 秒）
首 token / 输出速度0.8 秒 / 31 tok/s
缓存命中98%
token 用量输入 844K · 输出 37.1K
最终产物约 800 行代码

输入输出比为 23:1，原因是 agent 每一步都需将整段历史重新发送，输入量呈平方级累积。因此 98% 的前缀缓存命中率是性能的决定性因素：844K 输入中实际执行 prefill 的仅约 1.7 万 token，命中率若降至 90%，未命中量将升至 84K，prefill 工作量增至五倍。

瓶颈完全位于解码环节，LLM 耗时 20 分 05 秒而工具执行仅 25.8 秒。37.1K 输出除以 31 tok/s 约为 1197 秒，与实测基本吻合，因此估算耗时只需一个公式：任务耗时 ≈ 输出 token ÷ 解码速度。相同输出量在 150 tok/s 的托管服务上只需 4 分钟。另外这 37.1K 输出最终仅产出约 800 行代码，按 JavaScript 每行 10~12 token 粗略估算，约四分之三的输出用于思考过程、工具调用参数与中间返工。

产物

模型选择了 Vite 7 加原生 Canvas，理由是 Canvas 渲染最为直接、帧率最高，且无需 React 一类运行时框架。

代码没有集中堆在单个 index.html 中，四个源文件合计 800 行上下。其中 sound.js 是 prompt 未提及的，由模型自行添加。

第一版为标准实现：暗色渐变背景、圆角发光方块、分数等级消行统计、下一块预览与按键说明。

第二版额外实现了 HOLD 暂存位、NEXT 队列一次预览三块、幽灵方块落点预览、历史最高分与音效开关，按键扩展至 C / P / M / R，这些均不在 prompt 要求之内。

两版实测下来，旋转碰撞、踢墙、消行与计分均正常。二者的差异更多来自 harness 而非模型本身，不同客户端的 system prompt、工具集与规划策略各不相同。更换 harness 带来的效果差异，可能大于更换模型。

八、并发压测

前面几节的数值都来自单会话，无法反映多用户同时使用时的表现。用 vllm bench serve 打一轮固定负载：100 条请求，输入 512 / 输出 256 token，请求速率 10 RPS，并发上限 32，temperature 0。

结论与第四节一致：并发提升的是集群总吞吐而非单用户体验。32 人同时使用时，聚合吞吐涨到约 419 tok/s，但每人只分到 16 tok/s，且首 token 要等 2 秒以上。这套配置适合吞吐优先的离线批处理，交互式多用户场景则需要下调并发或接受更长的响应延迟。

九、成本核算

核算之前需先区分两个常被混淆的量，否则结论会整体失真。

844K 是 23 次请求的累加值，并非上下文窗口。窗口约束的是单次请求可容纳的长度，而累计 token 是把 23 次调用的输入分别相加，同一批历史被反复计费，因此累计值必然远大于窗口。

单次峰值可以反推：上下文近似线性增长，累加值约等于 步数 × 峰值 ÷ 2，得到峰值约为 844K ÷ 23 × 2 ≈ 73K。--max-model-len 262144 全程未用到一半，第四节日志中 KV 水位仅 9% 也印证了这一点。

窗口一致是两侧 token 可比的前提。73K 在主流的 128K/256K 窗口中均可容纳，因此本次两侧确为同一数量。但只要 API 一侧窗口更小，或主动限制上下文长度，harness 就必须中途压缩历史，届时 token 总量会变化，前缀缓存也会因前缀不再逐字一致而全部失效。

维度本地 4×RTX 3090官方托管 API（同规格）
单次上下文窗口262K，可自行设定，但需以 KV cache 预算为代价由厂商设定，通常 128K~256K
本次任务峰值上下文约 73K约 73K
全任务累计 token输入 844K · 输出 37.1K窗口足够、不触发压缩时才相同
解码速度 / 耗时29 tok/s · 20 分 05 秒约 150 tok/s · 约 4 分
单任务边际成本电费约 ¥0.26约 ¥1.5（$0.21）
前期投入约 ¥30,000¥0

成本算法列出如下，便于替换为自己的数值重新计算。API 侧按混合价 0.24/M计，(844K+37.1K)×0.24/M 计，(844K + 37.1K) × 0.24/M计，(844K+37.1K)×0.24/M ≈ $0.21；本地侧按 4 张卡实测 270~288W、整机 1.3kW 计，运行 20 分钟即 0.43 kWh，按 ¥0.6/kWh 得 ¥0.26。

仅看边际成本，本地约便宜 6 倍，但代价是 5 倍的时间。此外 ¥30,000 的前期投入需要约 2.4 万次同等规模的任务才能收回，按每天 10 个任务计需要 6.6 年。

换个角度验证：Qwen3.8-27B 一行即便按 2000 万 token/日 的高强度使用，回本周期仍需 6.1 年，与上文由电费独立推算出的 6.6 年基本一致，而硬件通常三年即面临换代。同表中的 Qwen3-Coder-Next 80B 为 MoE 架构，激活参数仅 3B，输出速度 149 tok/s，回本周期 1.5 年。差距的根源正在于稠密结构：稠密模型每生成一个 token 都需读取全部 27B 参数，而同级 MoE 只需读取激活的 3B。

另有一点值得注意，本地部署反而可能使 token 用量上升。按 token 计费时使用者会主动压缩上下文，本地缺少这一价格信号，262K 窗口一经开启便倾向于保留全部历史，前述 844K 输入中有相当一部分正是因无计费压力而未做清理。

结论是，若以节省 API 费用为目的进行本地部署，这笔账在多数情况下难以成立，稠密模型尤其处于劣势。真正成立的理由在于其他方面：数据不出内网、不受速率限制、可修改推理逻辑、便于研究。
