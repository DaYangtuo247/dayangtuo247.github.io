Pi Agent Core 架构剖析

人工智能工程实践 # AI Agent# TypeScript# 架构设计
Aug 19, 2026
19 min read
—

Pi 是 Mario Zechner 写的极简 TypeScript agent harness，是 OpenClaw 等一批编程 agent 背后的执行内核。这篇文档将解析Pi agent core，只画状态机、画泳道图，然后对照 packages/agent/src/agent-loop.ts 的真实源码逐段拆解——这个文件在 GitHub 上 805 行，是整个 agent 的”心脏”。

TypeScript · MIT License · badlogic/pi-mono · 核心 loop ≈300 行

三层架构总览

pi-mono 是个 monorepo，四个包按依赖关系分层。越往下越通用（LLM 通信），越往上越具体（终端 UI、会话管理）。要学的”agent 逻辑”全部在第二层。

依赖方向自上而下 · pi-agent-core 不认识任何具体 LLM 厂商，只认识 pi-ai 抛出的统一事件流

换句话说：pi-coding-agent 只是 pi-agent-core 的一个”重度用户”——它往 agent loop 里塞了 4 个工具（read / write / edit / bash）和一堆工程设施（会话存盘、终端渲染），核心决策循环完全不属于它。这也是为什么只需要吃透中间那一层。

Agent Loop 状态机

这是 runLoop() 函数（agent-loop.ts 第 190 行左右开始）的真实控制流，不是简化版。注意它是双层循环：内层处理”工具调用没跑完”，外层处理”用户在 agent 停下后又发了新消息”。

红框 = 唯一出口(agent_end) · 橙色 = 工具执行分支(内层循环) · 绿色虚线 = 外层循环(处理”agent 停下后用户又发消息”)

这张图对应”循环终止条件”——Pi 的终止条件不是一个，而是三层判断：① LLM 是否报错/被中断，② 这一轮有没有新的工具调用要执行，③ 业务层的 shouldStopAfterTurn 回调是否说”够了”。真正跳出双层循环，靠的是最后那次 return，而不是某个计数器。

一轮对话的泳道图

把状态机换个视角看：谁在什么时候跟谁通信。这张图画的是”用户输入 → 一次工具调用 → 得到答案”的完整单轮时序。

虚线处正是状态机里”hasMoreToolCalls=true → 回到 turn_start”的那条回边

源码逐段拆解

以下摘自 packages/agent/src/agent-loop.ts（MIT 协议，节选核心逻辑，省略部分类型定义）。对照着上面两张图看。

4.1 循环的入口：runLoop()

async function runLoop(
  initialContext: AgentContext,
  newMessages: AgentMessage[],
  initialConfig: AgentLoopConfig,
  signal: AbortSignal | undefined,
  emit: AgentEventSink,
  streamFunction: StreamFn,
): Promise<void> {
  let currentContext = initialContext;
  let config = initialConfig;
  let firstTurn = true;

  // 开始前先看看用户是不是在等待时又打了字（"打断"用的消息队列）
  let pendingMessages = (await config.getSteeringMessages?.()) || [];

  // 外层循环：agent 已经想停下了，但如果有排队的新消息，就continue
  while (true) {
    let hasMoreToolCalls = true;

    // 内层循环：只要还有工具调用没跑完，就继续转
    while (hasMoreToolCalls || pendingMessages.length > 0) {
      if (!firstTurn) { await emit({ type: "turn_start" }); }
      else { firstTurn = false; }

      // 把排队消息插入历史，再进入下一轮 assistant 响应
      if (pendingMessages.length > 0) {
        for (const message of pendingMessages) {
          currentContext.messages.push(message);
          newMessages.push(message);
        }
        pendingMessages = [];
      }

      // 核心一步：调 LLM，流式拿回一条 assistant 消息
      const message = await streamAssistantResponse(
        currentContext, config, signal, emit, streamFunction
      );
      newMessages.push(message);

      if (message.stopReason === "error" || message.stopReason === "aborted") {
        await emit({ type: "agent_end", messages: newMessages });
        return; // 唯一的异常出口
      }

      const toolCalls = message.content.filter(c => c.type === "toolCall");
      let toolResults: ToolResultMessage[] = [];
      hasMoreToolCalls = false;

      if (toolCalls.length > 0) {
        // 执行工具，拿到结果，塞回消息历史
        const batch = await executeToolCalls(currentContext, message, config, signal, emit);
        toolResults.push(...batch.messages);
        hasMoreToolCalls = !batch.terminate;
        for (const r of toolResults) {
          currentContext.messages.push(r);
          newMessages.push(r);
        }
      }

      // 业务层可以在这里插手：换模型、改 context、决定要不要停
      const snapshot = await config.prepareNextTurn?.({ message, toolResults, context: currentContext, newMessages });
      if (snapshot) { /* 应用 snapshot 覆盖 context/model */ }

      if (await config.shouldStopAfterTurn?.({ message, toolResults, context: currentContext, newMessages })) {
        await emit({ type: "agent_end", messages: newMessages });
        return; // 唯一的正常出口
      }

      pendingMessages = (await config.getSteeringMessages?.()) || [];
    }

    // 内层循环退出了（agent 想停）—— 看看有没有排队的 followUp
    const followUpMessages = (await config.getFollowUpMessages?.()) || [];
    if (followUpMessages.length > 0) {
      pendingMessages = followUpMessages;
      continue; // 回到外层 while(true)，等价于回到 turn_start
    }
    break; // 彻底没事干了，跳出外层
  }
  await emit({ type: "agent_end", messages: newMessages });
}

对应状态机：这一整个函数就是上面那张状态机图。hasMoreToolCalls 驱动内层循环（橙色回边），followUpMessages 驱动外层循环（绿色虚线回边）。

两个出口：全函数只有两处 return：LLM 报错/被中断，或者 shouldStopAfterTurn 说”够了”。没有 hardcode 的最大步数——最大步数是调用方通过这个回调自己实现的。

4.2 工具怎么被”翻译”成真正的调用：prepareToolCall()

async function prepareToolCall(
  currentContext: AgentContext,
  assistantMessage: AssistantMessage,
  toolCall: AgentToolCall,
  config: AgentLoopConfig,
  signal: AbortSignal | undefined,
) {
  // 1. 按 name 在已注册工具表里查（本质就是个 dispatch table）
  const tool = currentContext.tools?.find(t => t.name === toolCall.name);
  if (!tool) {
    return { kind: "immediate", result: createErrorToolResult(`Tool ${toolCall.name} not found`), isError: true };
  }

  // 2. 校验 LLM 给的参数是否符合这个工具的 JSON Schema
  const validatedArgs = validateToolArguments(tool, toolCall);

  // 3. 执行前钩子：业务层可以在这里拦截/拒绝一次工具调用
  if (config.beforeToolCall) {
    const beforeResult = await config.beforeToolCall({ assistantMessage, toolCall, args: validatedArgs, context: currentContext }, signal);
    if (beforeResult?.block) {
      return { kind: "immediate", result: createErrorToolResult(beforeResult.reason || "blocked"), isError: true };
    }
  }
  return { kind: "prepared", toolCall, tool, args: validatedArgs };
}

这段代码回答了”工具调用本质是什么”——就是按名字在一张表里查函数指针，校验参数，然后执行，跟用 C++ 写的 std::unordered_map<string, std::function<...>> 没有本质区别。beforeToolCall 这个钩子就是安全护栏挂载点——比如”危险命令要用户确认”就是在这里实现的。

4.3 并行 vs 串行执行

Pi 默认并行执行同一轮里的多个工具调用（executeToolCallsParallel，用 Promise.all），但只要有一个工具声明了 executionMode === "sequential"，这一批就整体退化为串行：

async function executeToolCalls(currentContext, assistantMessage, config, signal, emit) {
  const toolCalls = assistantMessage.content.filter(c => c.type === "toolCall");

  // 只要有一个工具要求串行（比如写文件、改状态），整批就退化为串行
  const hasSequentialToolCall = toolCalls.some(
    tc => currentContext.tools?.find(t => t.name === tc.name)?.executionMode === "sequential"
  );

  if (config.toolExecution === "sequential" || hasSequentialToolCall) {
    return executeToolCallsSequential(currentContext, assistantMessage, toolCalls, config, signal, emit);
  }
  return executeToolCallsParallel(currentContext, assistantMessage, toolCalls, config, signal, emit);
}

这是个面试可以直接拿来用的知识点：agent 并发执行工具会有副作用冲突的风险（比如两个工具同时写同一个文件），Pi 的解法是”工具自己声明能不能并行”，而不是框架层强行加锁——设计权衡交给使用者。

三个值得记住的设计决策

决策解决的问题代码位置
Steering Queue（打断队列）用户在 agent 还没吐完这一轮回答时又发了新消息（“等等，先别删”）——不能粗暴打断流式输出，得在下一个安全点插入getSteeringMessages()，每次内层循环开始前检查一次
Follow-up Queue（续接队列）agent 已经决定”这轮结束了”，但用户此时又发来新消息——不应该开一个全新的 agent_start，而是无缝续在同一次运行里getFollowUpMessages()，只在内层循环耗尽后检查
截断保护（stopReason === “length”）如果 LLM 输出被 token 上限截断，工具调用的参数可能是不完整的 JSON——直接执行有风险（比如一半的 rm 命令），所以整批直接判失败，让模型重新发failToolCallsFromTruncatedMessage()

注意：这三点是”工程壳”的例子——对应”agent = 循环 + 状态 + 工具”的内核，Steering/Follow-up/截断保护都不改变内核逻辑，它们是把一个”能跑的 demo”打磨成”能在真实交互里不崩”的产品所必须补的边界情况。这正是 LangGraph 这类框架要解决的同一类问题（可中断、可恢复），只是 Pi 用一个更轻的方式（几个队列 + 回调）实现，而不是显式状态图。

和已经会的 ReAct loop 对比一下

确认一下理解闭环了没有——把 Pi 的真实代码压缩回最初那个”想→做→看结果→再想”的伪代码，是这样的对应关系：

state = [user_prompt]
while True:
    response = llm(state)              # ↔ streamAssistantResponse()
    if response.is_final_answer:       # ↔ toolCalls.length === 0
        return response
    action = parse_action(response)    # ↔ message.content.filter(toolCall)
    result = dispatch(action)          # ↔ prepareToolCall() + tool.execute()
    state.append(action, result)       # ↔ currentContext.messages.push(...)
                                        # 循环 ↔ hasMoreToolCalls = true，回到 while 顶部

Pi 的 805 行代码，去掉事件流(EventStream)、打断队列、续接队列、并行执行、截断保护这些”工程壳”，内核就是这 7 行。这也是为什么不需要把 805 行都读完——要抓的是这 7 行对应的骨架，剩下的都是”怎么让这 7 行在真实世界里不崩”的工程细节，跟 LangGraph 解决的问题是同一类，只是实现方式不同（显式状态图 vs 命令式循环+回调）。
